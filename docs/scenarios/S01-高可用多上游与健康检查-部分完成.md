# S01 高可用多上游与健康检查

> 状态：部分完成

## 1. 场景描述

网关为同一应用配置多个上游服务器：主备切换（主不可用自动切备）、多目标轮询
负载均衡、上游健康检查（主动探测 + 被动失败计数），并提供缺省前缀转写
（strip / replace / add）与按上游组选择目标。

典型用户：后端有 2+ 副本或主备数据库/服务的团队，希望网关统一做故障转移，
不需要改 Caddyfile。

## 2. 现状分析

### 已完成

- 上游组（round_robin / active_standby）与目标（role = active / standby /
  round_robin），SQLite 存储、APCu 缓存。
- 主动探测 `Upstream::probeAll()`（导入器每分钟跑，GET check_path）与被动失败
  计数 `Upstream::markResult()`（filter 阶段按 5xx 累计，阈值可配）。
- 每请求在 access 阶段选出目标地址，通过 `X-Processor-Backend` 交给 Caddy
  单点转发（[Contract.php](../../processor/src/Contract.php:68)）。
- 前缀映射（strip / replace / add）与按组名选目标
  （[Upstream.php](../../processor/src/Upstream.php:62)）。
- 管理 UI：应用详情 → 上游（组/目标 CRUD、策略、健康检查参数、路径映射）。

### 未完成 / 缺口

- 目标 `weight` 字段有存储与界面，但选择逻辑未使用（实际为等权轮询）。
- `check_mode`（active/passive/both）未参与分支，实际恒为主动+被动都执行。
- 健康/轮询计数在 APCu（单机进程内），多网关实例部署时各自计数。
- 动态占位符上游不能带 scheme，目前按 HTTP 拨号转发；HTTPS 上游需另行处理。
- 全部目标不健康时当前为 fail-open（直连兜底），如需 fail-closed 需改策略。

## 3. 设置方法

管理 UI：应用详情 → 上游 → 新建上游组 → 添加目标。

等价 REST（需管理员会话 Cookie）：

```bash
# 上游组：轮询策略 + 缺省剥离 base_path
curl -s -X POST http://host/admin/api/apps/{appId}/upstreams \
  -H 'Content-Type: application/json' \
  -d '{"name":"订单上游","strategy":"round_robin","path_mode":"strip",
       "check_mode":"both","check_interval":10,"check_timeout":2,
       "check_path":"/healthz","fail_threshold":3,"recover_threshold":2}'

# 两个轮询目标
curl -s -X POST http://host/admin/api/apps/{appId}/upstreams/{gid}/targets \
  -H 'Content-Type: application/json' \
  -d '{"address":"http://10.0.0.1:9000","role":"round_robin","weight":100}'
curl -s -X POST http://host/admin/api/apps/{appId}/upstreams/{gid}/targets \
  -H 'Content-Type: application/json' \
  -d '{"address":"http://10.0.0.2:9000","role":"round_robin","weight":100}'
```

主备切换：把 `strategy` 改为 `active_standby`，目标 role 分别设为
`active` / `standby`。路径映射参考 [RULES.md](../RULES.md) 3.6 节与
`Upstream::mapPath()` 的 strip / replace / add。

## 4. 测试方法

### 自动化

```bash
php processor/tests/run.php
```

覆盖：`test_upstream_round_robin`、`test_upstream_active_standby`、
`test_upstream_passive_health`、`test_upstream_backend_by_name`、
`test_upstream_map_path`（见
[upstream_test.php](../../processor/tests/upstream_test.php)）。

### 手工 / E2E

1. 起两个 mock 上游（如 `python test/upstream.py` 不同端口）。
2. 配置轮询组两个目标；反复 curl 应用下接口，观察后端交替收到请求。
3. 关掉主目标 3 次以上（被动阈值 3）或让其 /healthz 失败，轮询组应不再选它；
   主备组应切到 standby。
4. 恢复主目标并连续成功 2 次，确认重新参与选择。
5. `/admin/api/metrics` 应输出 `gatekeeper_upstream_healthy` gauge 0/1。

预期：转发正常、无 502；健康状态随故障/恢复翻转。
