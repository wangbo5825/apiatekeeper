# S05 恶意扫描行为检测（占比/结构）

> 状态：未完成

## 1. 场景描述

检测单个 API 的访问量占全部访问的比例、客户端访问分布等行为结构，超过阈值
判定为疑似恶意扫描/爬取，触发告警或自动限制。

典型案例：

- 某客户端在一个窗口内大量访问同一个（通常是低频高价值）API，占比异常。
- 单 API 占总访问比例突增（如瞬时占 90%）。
- 大量请求命中不存在的路径（见 S06 的清单匹配与 S19 特征拦截）。

## 2. 现状分析

- **未实现**：没有任何占比/结构检测规则，也没有"命中即告警/拉黑"的联动。
- 数据基础已具备：request_logs 逐条记录 api_template / client_key / status；
  api_stats 有每 API 每小时的 requests 汇总，可离线计算单 API 占比。
- 在线（热路径）无窗口级"API 总数 vs 单 API 数"计数。
- client_stats 只有客户端×应用，**没有客户端×API 维度**，无法直接查
  "某客户端集中打某 API"。

## 3. 设置方法（规划方案，待实现）

目标配置形态（示意）：

```json
{
  "name": "单API占比检测",
  "api_pattern": "GET /export/*",
  "action_type": "api_share_check",
  "params": {
    "window": 300,
    "share_max": 0.8,
    "min_requests": 50,
    "action": "notify|blacklist_30m"
  }
}
```

实现建议：

1. 热路径维护 APCu 窗口计数（app 总请求 / 单 API 请求 / 单客户端×API）。
2. 新增 access 规则类型 `api_share_check`，超阈值返回 429/403 或写事件文件。
3. 事件复用 Blacklist 的 events 文件与后台持久化通道。
4. 或由后台分析器读 api_stats/request_logs 定期判定，只做告警/报表（离线）。

## 4. 测试方法（验收标准，待实现）

1. 构造脚本：某客户端窗口内对 `/export/{id}` 请求 100 次，同时对其他 API 共
   请求 <25 次，使占比 >80%。
2. 断言：命中检测规则 → 返回预期状态码（或产生告警事件/自动拉黑）。
3. 对照组：正常均匀访问流量不应误判（占比低于阈值时全部放行）。
4. 单元测试：直接调用检测类，覆盖边界（min_requests 未达、窗口滑动、占比恰好
   等于阈值）。

## 5. 后续工作

- 确定检测粒度：单客户端视角 vs 全局单 API 占比；在线 vs 离线。
- 需要 client×api 统计表（client_stats 增加 api_id 维度）或独立计数。
- 误报控制：min_requests 下限、白名单维度、观察期（多次命中才动作）。
