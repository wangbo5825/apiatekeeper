# S13 跨请求变量闭环（登录态/一次性许可）

> 状态：已完成

## 1. 场景描述

网关在请求间保存"按 key + TTL"的关联变量，实现跨请求状态闭环：

- 先调用 A 接口拿到/校验某个值（code/token/URL 参数），网关按 IP/用户保存；
- 后续 B 接口凭该变量存在/值匹配才放行；
- 典型业务：换票码、一次性许可、登录响应里保存会话令牌供后续接口校验。

这是与 Kong/APISIX 相比的差异化能力（两者需自写 Lua/Redis）。

## 2. 现状分析

- 变量声明区：应用内声明 name / key 维度（req.ip / dim:user / req.query:* 等）/
  TTL（[Variables.php](../../processor/src/Variables.php)、
  [Context.php](../../processor/src/Context.php:78)）。
- 写入：access 的 save_variable 规则（请求属性 → 变量）、filter 的
  response_transform op=save_variable（响应 JSON 属性 → 变量）。
- 校验：variable_check 规则（存在 / require_value / min_ttl 接口预留）
  （[RuleEngine.php](../../processor/src/RuleEngine.php:222)）。
- 管理 UI：应用详情 → 变量（声明）与规则表单。

## 3. 设置方法

管理 UI：应用详情 → 变量：声明变量；应用详情 → 规则：save_variable /
variable_check。

等价 REST：

```bash
# 1) 声明变量 code：按 IP 维度，TTL 300s
POST /admin/api/apps/{appId}/variables
  {"name":"code","key_dim":"req.ip","source":"","ttl":300}

# 2) A 接口：保存 query 里的 code
POST /admin/api/apps/{appId}/rules
  {"name":"保存验证码","api_pattern":"GET /v1/issue",
   "action_type":"save_variable","phase":"access",
   "params":{"name":"code","from":"req.query:code","ttl":300}}

# 3) B 接口：校验变量存在且等于 abc123
POST /admin/api/apps/{appId}/rules
  {"name":"校验许可","api_pattern":"GET /v1/use",
   "action_type":"variable_check","phase":"access",
   "params":{"name":"code","require_value":"abc123"}}
```

响应存变量的例子：filter 规则
`{"op":"save_variable","path":"data.token","target":"last_token",
  "key":"req.userid","ttl":3600}`（需先声明 last_token）。

## 4. 测试方法

### 自动化

```bash
php processor/tests/run.php
```

覆盖 variables_test.php 与 ruleengine_test.php（save/check 流程）。

### 手工

1. 同 IP 请求 `/v1/issue?code=abc123` → 200。
2. 同 IP 请求 `/v1/use` → 200（放行）；无前置请求的 IP → 403。
3. TTL 过期后同一流程重新 403。
4. 换 IP 请求 `/v1/use` → 403（key 维度隔离正确）。

预期：跨请求状态按 key 维度生效且过期失效。
