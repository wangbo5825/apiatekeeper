# S23 请求追踪与规则命中调试

> 状态：部分完成

## 1. 场景描述

每个请求有贯穿 access/filter 的唯一 ID；排查问题时能回答：某请求命中了哪些
规则、为什么放行/拒绝、走到了哪个上游、响应状态如何（"规则命中调试视图"）。

## 2. 现状分析

### 已完成

- caddy-access-filter 为同一请求的 access/filter 生成一致请求 id（新二进制），
  并写入日志/上下文（X-Request-Id）。
- request_logs 以 id 为主键，逐条含 app / api_template / status / upstream /
  duration；系统页展示记录链路实时状态（行数/滞后）。
- 记录被拒绝请求（recordDenied）与 Metrics 拦截原因。

### 未完成 / 缺口

- 管理端没有"按请求 ID 查单条链路 + 规则命中明细"的视图。
- 规则级"匹配了什么、执行结果"没有逐请求落库（只有最终记录/拒绝）。
- X-Request-Id 当前写回请求头并随请求转发，存在信息外泄（ISSUES 计划改进为
  内部传递）。

## 3. 设置方法

暂无专门管理入口；可用的现有查询：

```bash
# 日志文件按天检索请求 id / api
grep '<request-id>' data/logs/$(date +%F).log

# SQLite 检索
sqlite3 data/apigate.sqlite \
  "SELECT id,ts,app_id,api_template,status,duration_ms,upstream
   FROM request_logs WHERE id='<request-id>' OR api_template LIKE '%x%' ORDER BY ts DESC LIMIT 50"
```

规划入口：系统页新增"按请求 ID / 时间段查询"，展示 access 决策 JSON（matched
rules、deny、route）+ filter 结果。

## 4. 测试方法

1. 发一个请求并记录响应/请求头里的 X-Request-Id。
2. 日志与 request_logs 存在同 id 一行，字段与真实请求一致。
3. 分别发一个被 429/403/404 的请求，确认 recordDenied 记录存在。
4. 规划验收：调试视图输入 id 后展示命中的规则与"为何拒绝"。
