# S12 内网外网双通道隔离

> 状态：已完成

## 1. 场景描述

同一网关同时服务两类入口：面向公网的 API（走认证/限流/缓存治理）与面向内网的
管理/运维接口（IP 白名单直通），互不串扰；外网请求内网接口被拒。

## 2. 现状分析

该场景由现有能力**组合**实现：

- 多应用按 base_path / Host / 请求头匹配（[App.php](../../processor/src/App.php:58)）。
- Caddyfile 用 `remote_ip` 匹配器对 /ops 入口做来源限制（网关现有处理器路由
  已使用该语法），应用级 default_allow 决定未登记路径是否放行。
- 上游组/缺省映射决定每个应用去哪个后端。

说明：规则层 client_pattern 只能限定"规则作用于谁"，不能表达"排除某网段"，
所以"仅内网"的边界判断放在 Caddy 层完成，规则层负责其余治理（限流/认证/
审计）。

## 3. 设置方法

例：`/open` 应用对外、`/ops` 应用对内。

Caddyfile（configs/Caddyfile 或独立片段）先做来源限制：

```caddy
:8080 {
	# /ops 仅允许内网来源（放在默认网关 handle 之前）
	@opsExternal {
		path /ops*
		not remote_ip 10.0.0.0/8 127.0.0.0/8 ::1
	}
	respond @opsExternal 403
}
```

```bash
# 1) 建两个应用
POST /admin/api/apps  {"name":"开放API","base_path":"/open"}
POST /admin/api/apps  {"name":"运维接口","base_path":"/ops","default_allow":0}

# 2) 各自配上游组与所需规则（限流/认证只加在 /open）
```

若同一路径要"外网限流、内网不限"，可在规则层对 /open 配 rate_limit +
client_pattern=`ip:10.0.0.0/8` 的效果相反（限的是内网），因此需等 client_pattern
取反或 ACL 语义（见 S08 第 5 节）后才适合用规则表达。

## 4. 测试方法

1. 本机（127.0.0.1）请求 `/ops/*` → 放行。
2. 非 10.0.0.0/8 来源请求 `/ops/*` → Caddy 403，且不会进入网关规则链。
3. `/open/*` 无 IP 限制，只受其自身认证/限流规则约束。
4. 确认两个应用的统计/规则/上游完全隔离（app_id 维度）。

预期：内外流量各走各的应用策略，接口不串。

## 5. 后续工作

- 若需要"同一入口按客户端来源分流"，可结合 S16 的动态路由。
- mTLS/双向证书鉴别（外部能力，不在 PHP 规则层）可作增强。
